Owner requirement (2026-10-19), which is the acceptance of this task: in the terminal, never a web page, for every running or finished milestone attempt the owner sees (1) elapsed minutes, (2) the current stage: node and review round, (3) whether it failed and the cause, (4) what to do next, (5) what the worker writes: a read-only, scrubbed tail of recent worker progress lines. Unavailable stage/round data is explicitly unknown; historical elapsed is explicitly approximate and is not presented as the completion time. Rules:
- R-1 One view, two UIs. `Delivery.run_view(r, streams, now)` is pure over the stored record plus the parsed streams (R-2). It returns plain catalog lines in this order: Время, Этап, Модели, Итог, Дальше, Токены, Последний прогресс (the seven summary fields), then the tail section(s). The TUI and the plain UI render the same lines. Nothing is computed in a widget.
  - Время. Active (submitted/running/stopping): "идёт D" from `created` to now. Terminal: show "до последней прочитанной записи журнала: D; время завершения неизвестно", calculated from created to the maximum timestamp of valid run-wide records read. This is an observation interval, not the run duration. Missing created, no valid timestamp, or a timestamp before created gives "длительность: нет данных". Use "длилась ≈D" only when the UI also states this limitation. D uses `live.duration`; never negative.
  - Этап. Show every currently observed node, retaining its node identifier alongside its catalog role. A task is shown only when the execution-to-task association is proven; otherwise "задача: нет данных". Review round and observed counters: s9a2 R-1. Never attach live.task to an unproven execution. Terminal records show the last observed stage, explicitly labelled as observed, or "нет данных". Do not infer stage or round from log prose.
  - Модели. One entry per observed node: "<node> (<role>): задано M/E; фактически: нет данных". Node -> role through the existing milestone graph role map (not a second table); a node the map does not bind -> "задано: нет данных". A terminal record shows the three configured bindings with the same "фактически: нет данных". The configured binding is never labelled as the one actually used.
  - Итог. Active: "ещё идёт". A detached observation reads "наблюдение прервано — состояние неизвестно, [w] подключиться" and never failed or finished. Terminal: the state text of `run_state` plus, for failed/failed_recoverable, the S4 catalog line verbatim (observational prefix, class, remedy, reset). Failure is never inferred from a log line or level.
  - Дальше. The same mapping home and RunScreen use (`next_step` / END_ACTIONS after polish-04): one function, no second table. Historical attempts: s9a2 R-2.
  - Токены. Active: "Токены: нет данных до завершения". Terminal: S2c `usage_line(r.get("usage"))`.
  - Последний прогресс. P = max(`live.last_event`, newest valid run-wide record timestamp), rendered "HH:MM:SS (D назад)", or "нет данных" when neither exists. Stall: an active attempt with now - P >= STALL_SECONDS (900) shows "нет прогресса с HH:MM:SS (D)". Display-only, no action. A run that writes log lines is not stalled. Home keeps its exact label «последнее событие» and promises no worker activity.
- R-2 Streams and tail grammar (closed).
  - Attribution. Preserve execution as structured metadata. Only a watch-proven execution-to-node association may identify worker output; message prefixes and log levels are not identity evidence. Observers may retain an optional bounded execution-to-node map of the last EXECUTIONS_LIMIT associations; legacy records remain valid. When a worker execution is known, read its tail through --execution. Otherwise show "Вывод прогона; принадлежность исполнителю не подтверждена". Run-wide records remain available for activity/time and are not labelled worker output. Each stream has its own cursor and bounds; terminal attempts receive at most one read per stream.
  - The map (`execution_nodes`), the stream identity/result contract and worker-stream selection: s9a1 R-1..R-3.
  - Grammar. Input: the reader's retained bytes (live.tail buffer and partial-first-line rules unchanged), cut on "\n" only. A line is a record iff it is one JSON object with: `cursor` a nonempty str; `timestamp` an int 0..2**53-1, bools rejected; `execution` absent or a str; `record` an object with `level` in the five values and `message` a str. Every other line is malformed: never shown, parsed for lifecycle or classified; when N > 0, one line "нераспознанных строк: N" follows that stream. A record renders as "HH:MM:SS  <tag><text>": local time of `timestamp`; tag "" for info, "ошибка: " for error, "предупреждение: " for warn, "служебное: " for debug/trace. Keep the last TAIL_LINES (40) records per stream, oldest first. No records: "Журнал пока пуст: Zeroshot ещё ничего не записал."; reader failure: "Журнал недоступен: <summary>".
  - Totality. JSON decoding, timestamp conversion and rendering are total over arbitrary retained bytes. Invalid UTF-8, excessive JSON nesting and invalid Unicode scalar values never escape as exceptions. A valid record with an unrenderable timestamp retains its message and shows "время: нет данных"; that timestamp does not participate in elapsed or stall calculations.
- R-3 Scrub of worker text (closed). Permitted output form: printable characters only, one line, at most TAIL_TEXT (300) characters plus "…". Steps, in order, on the decoded `message`:
  1. Remove terminal sequences. CSI = ESC [ or U+009B, parameter bytes 0x30-0x3F, intermediate bytes 0x20-0x2F, one final byte 0x40-0x7E; an unfinished CSI, or a recognized CSI prefix followed by syntax outside this grammar, discards the remainder. OSC/DCS/APC/PM/SOS = ESC ] P _ ^ X or U+009D U+0090 U+009F U+009E U+0098, up to BEL or ST (ESC \ or U+009C); unterminated discards the remainder. Any other ESC removes itself and the next character.
  2. Credential masking: `live.scrub`. Credential guarantees cover live.scrub's documented field/token grammar, not arbitrary secrets in prose.
  3. After credential masking, replace every character for which str.isprintable() is false with one space, collapse spaces and strip, then truncate (300 characters, "…" when cut); drop an empty result. Keep the existing sequence-removal-before-masking order.
  Render a literal Rich Text object, or a widget with markup=False. Text is never shown before steps 1-3. A credential split by a removed sequence (`api_key=\x1b[0mSECRET`) is masked because step 2 runs after step 1.
- R-4 Reader and refresh. Use the `live.tail` mechanics: bounded bytes, deadline, only the reader process is killed, its own session. The reader returns parsed records per stream. On open it reads each stream (`logs RUN`, and `logs RUN --execution REF` when R-2 knows a worker execution). The TUI view of an active attempt re-reads every TAIL_REFRESH (10 s) after the previous read ended, with `--after <cursor of that stream's newest valid record>`, appends and keeps the last 40 per stream. Reads are the existing coalesced, cuttable "tail" job; never from the home refresh or an observe slice; they write nothing to the run record (`live` stays written only by observers, live.py:1-7). While open, refresh the presentation from the latest stored attempt snapshot and current time, independently of whether logs produced new lines. A transition to terminal stops active refresh scheduling and permits one final read per stream. Closing invalidates pending callbacks. Closing or quitting cancels and reaps the reader within the remaining QUIT_BUDGET; only reader processes are terminated. A failed refresh keeps the shown lines and adds "журнал не обновлён: <summary>". No stop, resume, retry, model call, sqlite read or HTTP history call happens anywhere in this path.

The selected RunViewScreen is read-only; historical attempts cannot invoke current-attempt mutations. The plain UI offers the same selection. Titles include revision, milestone, attempt and a distinguishing run-id suffix.
  - [e] in the end modal opens the RunViewScreen of the modal's attempt directly. The RunViewScreen scrolls and closes with esc/q. Update `tailable`/`tail_item` and the key bars.
  - The planner tail keeps its entry point and uses the R-2/R-3 rendering only (run-wide stream, unattributed).
  - Layout: at both supported sizes, the seven summary fields occupy at most 14 terminal rows. Bound displayed field values using terminal-cell width and explicit ellipsis; full scrubbed values remain in scrollable details.
