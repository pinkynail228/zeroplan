Rules:
- R-1 Lane in a role binding. A role binding is {model, effort} plus an optional `lane`. The only accepted value is exactly `{"harness": "codex", "provider": "gateway"}`. Anything else is refused with the existing invalid-binding errors of each validator, with a remedy naming the accepted value: another harness or provider, extra keys, a non-object, or `connections`/`sessionScope` in a binding. Upstream canonical requirements are used, and zplan never writes `connections` into a runtime plan. All five validators of the audit accept the same shape through one shared definition. The architect role refuses `lane` (the architect runs Codex directly, outside the engine). A binding without `lane` keeps its exact bytes, so profiles and records from before S3 keep their digests.
- R-2 Runtime plan. A node whose role has `lane` gets exactly that `lane` in the runtime document, in both planner runtimes and the milestone runtime. Other nodes are byte-identical to the base. The run-level harness/provider stays codex/openai.
- R-3 Where lanes are set. The project zplan.process.json `roles.<name>.lane` (edited by hand, documented in docs/PROCESS_PROFILE.md), or the user's roles.json through `zplan roles`. `zplan roles` asks per role "lane [openai/gateway]"; Enter keeps the current lane, and `openai` removes `lane`. An existing lane is never dropped when only model or effort is edited. With a project profile, `zplan roles` still only shows the roles, now with their lane. `zplan profile` and doctor's roles line print the lane of each role that has one.
- R-6 Store check (one function). `connection_ready(engine, key, fields)` runs `<engine> connection list` with that engine's native env, timeout=30 seconds. Parse the pinned ConnectionListResult envelope and validate summary types before membership checks. Invalid envelopes or summaries produce lane.connection_unknown, never an uncaught exception. A nonzero exit or a timeout also gives `lane.connection_unknown`. Ready iff the result lists `key` with scope `user` and `fields ⊆ listed fields`; a missing key or field is not-ready. The function never calls `set` or `delete`. Connection metadata readiness does not validate the stored base URL or provider access; those validations belong to the native runner.
- R-7 Env is never the connection source. `NativeEngine.native_environment()` removes GATEWAY_BASE_URL and GATEWAY_API_KEY from the child env for every `zeroshot` call (run, validate, watch, status, resume, force-stop, logs, connection). That includes siblings from `engine_for` and `recorded_engine`. Every other variable is unchanged, including s2a's recorded CODEX_HOME. The stored connection is therefore the only source at start and on every resume. This is a deliberate compatibility change (critic decision 2). docs/INSTALLATION.md and docs/USER_FLOW.md document moving hand-set GATEWAY_* into the native store. When either variable is set in zplan's own env, doctor shows a WARN (S5a severity): "GATEWAY_* в окружении игнорируются zplan; источник — zeroshot connection store". Values are never printed.
- R-8 Preflight. Each of these checks the gateway connection with R-6: a fresh submission of a planning revision or milestone attempt whose runtime has a gateway `lane`; its `--validate-only`; and a resume whose recorded `connectionRequirements` contain the key `gateway`.
  - A failed or unknown connection preflight occurs before changing submission state, setting resume_pending, appending a successor or writing a resume journal entry. Native status reads are allowed. For resume, use the predecessor's fresh workspaceRecovery.connectionRequirements and recorded engine (`engine_for(binding)`, so the store of the record's own state root). In runs.py this means after the status read and before `r["recoverable"] = True`.
  - Deduplicate preflight within one action; resume performs exactly one connection list.
  - Not ready refuses with `lane.connection_missing`. The remedy is actionable and names the checked engine: `ZEROSHOT_STATE_DIR=<state_root>/runs <executable> connection set gateway --field GATEWAY_BASE_URL --field GATEWAY_API_KEY`, with that record's executable and state root. It must not reference a `zplan lane` command (s3b replaces this remedy).
  - Records without a gateway lane make no `connection list` call.
- R-10 (applicable part) No credential at rest outside the native store. zplan writes only names (`gateway`, GATEWAY_BASE_URL, GATEWAY_API_KEY) into its files: roles.json, the project profile, Authority state, run documents and receipts. Live/log output keeps the existing redaction. zplan never reads, captures or stores a connection value.
