tui-quit-race — the TUI worker must never block on the UI thread at quit; fix three flaky tests. Found by the full-suite qualification of g1b-override (pre-existing on main, diagnosed 2026-10-16). DeepSeek calibration rung 4, grade medium (product). Scope: terminal_planner/tui/app.py, terminal_planner/tui/controller.py, tests/ (test_tui*.py, test_terminal_planner.py). No docs, no other product module.

1. Product race (the real defect). `ZplanApp.from_worker` (terminal_planner/tui/app.py:940-948) checks `controller.closing` and then calls Textual `call_from_thread`, which blocks the worker until the UI thread runs the callback. If the worker has already passed the `closing` check when the UI thread enters `on_unmount` -> `Controller.stop()` (app.py:921-922, controller.py:180-188), the worker waits for a UI loop that is now joining it: `stop()` times out after STOP_WAIT (8 s), or never returns when `mutating()` was true (join without timeout, controller.py:188). The worker still holds the `Authority` (opened in `open_session`, controller.py:159), whose lock is per project + fixture (authority.py, `.locks` under the production root), so the next locked open fails with `BlockingIOError: [Errno 11]` -> `Blocked store.locked`. This is the Linux failure of tests/test_tui_live.py la3 (`PanelTests.test_la3_...`) and la5 at 80x24 (`KeyBarTests.test_la5_...`); la5 at 120x40 then opens an empty store and misses `[g] запустить` (same test, knock-on).
   Two different flags, keep them apart: `app.quitting` (quit requested while a mutating job runs; results are still delivered and shown on the FinishingScreen) and `controller.closing` (set by `stop()` at unmount; from then on nothing is delivered).
   Required behaviour (invariants; the design is yours, keep it small):
   - I-1 The worker thread never waits for the UI thread (no `call_from_thread` or any future/result wait in the delivery path). Use a non-blocking hand-over to the app's loop (e.g. `loop.call_soon_threadsafe` / `post_message`), with `controller.closing` re-checked on the UI side so nothing is delivered once closing has begun. While only `app.quitting` is set, delivery continues as today.
   - I-2 A mutating job's result is still shown before the app can exit: `mutating()` stays true until the job's delivery is finished, and the count is released exactly once per mutating job, at the first of: its UI handler returned, its UI handler raised, or its delivery was dropped because of `closing` (including callbacks already queued on the loop when closing began, and a loop that is already closed). Jobs with `done=None` and controller callbacks that are not UI hand-overs keep releasing right after `done()` on the worker. The worker does not wait for any of this. `action_quit`/`quit_when_idle`/FinishingScreen behaviour is unchanged.
   - I-3 The reproduced race is gone: when no job is stuck, `stop()` returns promptly after the job in flight ends and the session's `Authority` is closed (lock released) when it returns. The existing bounded shutdown for a stuck watch slice stays as it is (tests/test_tui_milestones.py:~518, STOP_WAIT); no new cancellation protocol.
   - I-4 A UI handler raising does not kill the worker or leave `_mutating` stuck.
2. Test defect: `read_pty` in tests/test_terminal_planner.py (~1573-1587) treats only OSError as EOF; on macOS the master returns `b""` after the child exits, so the loop busy-spins for its whole 20 s deadline (every Mac run of the real-PTY tests burns a core ~20 s). Treat `b""` as EOF, keeping the output read so far. Apply the same to any sibling PTY reader in tests/ with the same pattern (tests/test_tui.py:~95 already handles it).
3. Test threshold: tests/test_tui.py `ResponsivenessTests.test_a4_a_slow_setup_keeps_settings_responsive` asserts two `pilot.press` calls take < 0.5 s (test_tui.py:422); they take 0.23-0.33 s unloaded and 0.67 s were seen under full-suite load. Raise the bound to 2.0 s with a comment (it guards against the UI blocking for the setup's 3 s `release.wait(3)`), keeping the check that the setup is still running. Same review for the sibling `< 0.5` at test_tui.py:~402 (same fix only if it measures pilot presses against a multi-second block).
