# T2 design: rebuild the shallow tests, keep the deep ones

Status: revision 2, accepted by the owner on 2026-11-04 (keep the deep tests, rebuild the shallow ones in
ledgered batches; no size ratio as a goal). After one Goldfish pass on revision 1 (`.local/goldfish/2026-11-04-t2-tests/`:
comprehension, design_critic, zoom_out; section 7 resolves them). Revision 1 replaced the whole suite beside the old
one and switched in one commit; review showed that the proof it relied on is the kind the 2026-10-28 audit already
found unsafe, and that its size and time targets contradicted the adversarial tests it promised to keep. Revision 2
narrows "from scratch" to the layers that are wrong and asks the owner to confirm that narrowing (section 6).
Evidence (private): `.local/a0/T2-R1.md`, `.local/test-review/` (the audit, `bugs.jsonl`, `mut.jsonl`).

## 1. Problem

- 143 modules, 68,068 test lines against 36,412 product lines, 2698 tests, a 449 s full lane, 1482 sentence
  assertions. A product change breaks pins that are not behaviour (A0's S1b: 15 pins for one prompt change).
- The suite has two kinds of tests. Deep ones guard what costs the owner's code or secrets: merge admission and the
  exact candidate, durability and replay, concurrency, scrubbing, process and filesystem safety. `T2-R1.md` classes
  about 23k lines as such (11 of the 20 largest modules, three mixed ones, nine smaller risk modules). Shallow ones
  pin screens, wording, private structure, and repeat other layers: most of the rest.
- Three cuts failed because no gate could see what a removed test protected (`T2-R1.md` section 1).

## 2. Goals and non-goals

- G1 No lost protection: every behaviour a removed module checked is either covered by a named new test or declared
  dropped with a reason, in a ledger a cold reviewer samples; held-out defects planted in the replaced areas by
  someone who never sees the new tests are all caught.
- G2 Behaviour, not wording: new tests assert results, records, visible states and exported constants; a sentence
  is asserted only where the owner must see those words.
- G3 Less friction: fewer tests broken by a change that does not change their behaviour (sentence pins), and a
  shorter wait for the run a worker or the merge needs; both measured per batch. No size ratio is a goal: lines of
  test code say nothing about protection (owner, 2026-11-04; DEVELOPMENT 4: no target number of tests).
- G4 Local: a change to one module can run the tests it affects (selection by code), if T2.0 shows the selection
  does not degenerate to "everything".

Non-goals: rewriting the deep tests (they stay, refactored only when touched); the evaluation rig; the slice
runner's own tests; coverage or mutation scores as targets; new dependencies; a second suite directory.

## 3. Design

### 3.1 Keep, replace, remove

| Kind | What happens | Proof |
|---|---|---|
| Deep (risk) modules | Stay as they are. They are the floor no batch may weaken. | None needed: nothing removed |
| Shallow modules (screens, wording, structure, duplicates) | Replaced, batch by batch, by journeys and contract tests | The batch ledger, a cold review, held-out defects (3.3) |
| Tests of removed product (the line UI, the planner path, goal drafts) | Leave with their code (the existing rule) | The ratchet's `removes` |

T2.0 classifies all 143 modules by test class (deep, shallow, removed-with-product), with the evidence for each; the
owner sees the list before the first deletion.

### 3.2 What the new tests are

- **Journeys**, one per job the owner does (talk and keep the history; goal to a checked plan and the yes; a
  non-linear run and its repair; merge only the verified candidate; kill and reopen; control without a model;
  delegated recovery; read the result; first run). Through the full-screen app with the scripted architect and the
  fixture engine, real Git and stores, at 80x24 and a wide size. The scripted architect is product surface behind
  `--fixture` (`architect.py` FixtureArchitect); extending it is a product change, reviewed as one. Install and
  upgrade stay with the installed qualification (DEVELOPMENT 4), not a journey.
- **Contract tests**, one module per product boundary a shallow module tested, through public functions.
- Rules: no new test imports another test module except `tests/support.py`; named for the behaviour; text only as
  G2 says.

### 3.3 One replacement batch

1. A worker writes the batch's ledger: for each replaced module, one line per behaviour it checks (following
   helpers), mapped to the new test that covers it or "dropped: reason".
2. The new journeys or contract tests land (ordinary slices, each within the slice limits).
3. A separate worker, given only the product code and the ledger's behaviour lines (never the new tests), writes
   held-out defect patches into `.local/t2/defects/`: at least two per replaced area, plus the known-lost checks the
   audit names (export refusals, connection verdicts, `test_autonomy.py:55`, `test_milestone.py:318`) where they
   fall in the batch. Each defect is confirmed red on the old suite.
4. `devtools/defect_replay.py` applies each defect (and each `bugs.jsonl` fix reverted, where it still applies) in a
   scratch worktree and runs the suite without the replaced modules; every defect must be caught; a kill is
   confirmed by a rerun on clean code.
5. One cold review (a fresh Opus, no tools beyond reading) samples the ledger against the deleted modules; more than
   1 lost check in 10 sampled stops the batch.
6. The batch deletes the replaced modules (ratchet `removes` naming the ledger), after the full lane on that tree.

This amends `docs/DEVELOPMENT.md` section 4 (removals need "an assertion inventory that follows helpers and one cold
review of the batch"): the ledger is that inventory, the review is that review, and the held-out defects are added.

### 3.4 Selection (G4)

`devtools/affected.py` maps test modules to product modules through imports, plus the paths tests load directly
(`check_guard.py`), the resources (`architect_method.md`, `agent_profile.toml`, `zplan.tcss`), and always the modules
that start subprocesses. T2.0 measures it on the last 30 commits; if a typical change selects more than half the
suite, G4 is dropped and the full lane stays the only run.

## 4. Alternatives

| Alternative | Verdict |
|---|---|
| Replace everything beside the old suite, switch in one commit (revision 1) | Rejected after review: the proof (fix replay and a few planted defects) is what the audit already found unsafe; the targets contradicted the deep tests; dozens of slices with two suites running |
| Prune with evidence, in place (a runtime oracle ledger and a mutation matrix) | Rejected: 8-12% for the cost of the evidence |
| Stop the growth only (the ratchet) | Done, not enough |
| Rewrite the deep tests too | Rejected: they are the part that works, and rewriting them is where protection is lost |

## 5. Risks

- **Less reduction than hoped.** The deep layer stays (about 23k lines); the gain is in the shallow layer, pins and
  time. Measured per batch; the owner sees the numbers.
- **Cost.** Each batch is a ledger, a few slices, a defect batch and a cold review; T2.0 estimates the batches.
- **The ratchet does not see pins in helpers or lambdas** (its known blind spot); the cold review samples for them.

## 7. Resolution of the Goldfish findings (revision 1)

| Finding | Resolution |
|---|---|
| The switch proof is what the audit found unsafe; DEVELOPMENT 4 needs an inventory and a cold review (D 1, Z 1) | Accepted: per-batch ledger, cold review with a stop rule, held-out defects from a separate worker, known-lost checks mandatory, a floor of 10 applicable fixes, reruns on clean code, the rule amended (3.3) |
| Size and time targets contradict the deep tests (D 2, C 2) | Accepted: deep tests kept; the size ratio dropped as a goal (the owner: a meaningless metric), friction and wait time measured instead |
| Moved tests break rule 3.2 and the guard (C 1, Z 2, D 5) | Accepted: nothing is moved; deep tests stay where they are |
| Selection misses resources, paths, subprocesses; may degenerate (D 6, Z 3, C 6) | Accepted: 3.4 adds them and a measured drop rule |
| The fixture claim was wrong; journeys under-scoped; jobs 5 and 9 (D 7, Z 4, C 7) | Accepted: the scripted architect is product surface; install and upgrade stay with qualification |
| `tests2/` invisible to tooling; the switch list (D 8, Z 6, C 5) | Accepted: no second directory |
| G4 measured the wrong thing; the ratchet's blind spot (D 9, Z 7, C 3) | Accepted: G2 is a rule plus the cold review; the blind spot is named |
| Slices break the limits; no cost or stop rule (D 10, Z 9) | Accepted: batches of ordinary slices, a per-batch stop rule, T2.0 estimates |
| Alternatives uneven (D 11, Z 10) | Accepted: section 4 rewritten |
| Line-UI removal not sequenced (Z 5) | Accepted: it leaves with its code before T2.1, in its own slice |
| Stale evidence, wrong citation, drifted numbers, reader gaps (D 12-17, C 4, C 9-12) | Accepted: numbers re-stated from the 2026-11-04 full lane; the main-gate rule is DEVELOPMENT 2.8 |
